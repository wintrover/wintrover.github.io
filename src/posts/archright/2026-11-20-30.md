In November 2026, nim-libp2p merged PR #3430. The change is one line in `libp2p/utils/bytesview.nim` and eleven lines of tests. It makes `BytesView.toOpenArray(b, e)` use inclusive bounds relative to the unconsumed data, and it closes issue #3364 — a report I filed with a counterexample produced by Axiom.

That merge is the achievement I want to record. A proposition about a real library was adopted explicitly, checked by a deterministic engine, and then confirmed by the project's own maintainers in their own code. Axiom did not push the fix; `richard-ramos` wrote it. That is the normal and correct shape of an upstream contribution.

The same audit produced a less comfortable result. When I went back to re-verify the verdict behind the issue, most of its public evidence was gone. The CI run returned 404. The release named in the reproduction instructions did not exist publicly when the evidence document was written. The `third-party cold replay` in my own issue comment was, by the evidence document's own description, my local replay.

This post records both halves. The fix survived; the verdict did not. The durable artifact is not Axiom's label but the regression test that now runs in nim-libp2p.

## Background: terminology

**BytesView** is nim-libp2p's non-owning view over a byte sequence. It holds a `seq[byte]` and a read position `rpos`; `len` is the number of unconsumed bytes. A view avoids copying when a protocol parses a frame, slices a field, or hands a buffer to a decoder.

**openArray** is Nim's borrowed-array parameter type: a pointer plus a length, with no ownership. `system.toOpenArray(x, first, last)` returns such a view over `x` from index `first` through index `last` inclusive. The Nim documentation is explicit about the convention, and its example is the one this story turns on:

```nim
proc test(x: openArray[int]) =
  doAssert x == [1, 2, 3]

let s = @[0, 1, 2, 3, 4]
s.toOpenArray(1, 3).test
```

**Bounded model checking (BMC)** turns a claim about a program into a satisfiability question over a bounded domain: is there an input, within the bound, for which the claim is false? A satisfiable answer comes with a model — a concrete counterexample. **CEGAR** (counterexample-guided abstraction refinement) starts with a coarse abstraction, checks it, and refines when a candidate counterexample turns out to be spurious.

**Axiom** is the verification engine this project builds. It takes an adopted proposition, lowers it to a solver query, records a verdict, and preserves a run record. Its stated scope is bounded: deterministic results within a supported kernel scope, not a full formal proof of every program property.

## 1) The subject and the arithmetic

The pre-fix subject was [`iftech/nim-libp2p`](https://github.com/iftech/nim-libp2p) at commit `a130a7f32219909bdcda14b7f1e64d0804fc832c`. The module under test was pinned by hash:

```text
libp2p/utils/bytesview.nim
sha256 b205c969ba04f4199d8fd4a121d4b6fccdc82c426e336add0e1e9fd0e961e5ee
```

The template read, before the fix:

```nim
template toOpenArray*(v: BytesView, b, e: int): openArray[byte] =
  v.data.toOpenArray(v.rpos + b, v.rpos + e - b)
```

The intent is a slice relative to the unconsumed data: `b` is the first relative index, `e` the last, both inclusive. The start is advanced by `b`. The end should also be advanced by `b` — but the expression subtracts it. At `rpos = 0`, the underlying inclusive range becomes `[b, e - b]`, whose length is `e - 2b + 1`. The inclusive law for a view-relative slice is `e - b + 1`. The result is exactly `b` elements short.

The fix removes the second subtraction:

```nim
template toOpenArray*(v: BytesView, b, e: int): openArray[byte] =
  v.data.toOpenArray(v.rpos + b, v.rpos + e)
```

The behavioral table for a view over `[1, 2, 3, 4, 5, 6]` at `rpos = 0` makes the gap visible:

| `b` | `e` | inclusive law (`e - b + 1`) | before fix (`e - 2b + 1`) | after fix |
|---|---|---|---|---|
| 0 | 4 | 5 | 5 | 5 |
| 1 | 1 | 1 | 0 | 1 |
| 1 | 3 | 3 | 2 | 3 |
| 1 | 4 | 4 | 3 | 4 |
| 1 | 5 | 5 | 4 | 5 |
| 2 | 5 | 4 | 2 | 4 |
| 4 | 5 | 2 | -2 | 2 |

At `b = 0` the two formulas coincide, which is why the defect could survive in production. Both production call sites are in `noise.nim` (`read_e` and `read_s`), and both pass a literal zero start. A caller with a nonzero start received a shorter view than it asked for, with no error and no signal. For `b = e > 0` the old formula produced a zero-length view for a valid one-element slice; for `2b > e` it could produce a negative length, which raises a `RangeDefect` when materialized into a sequence. The fix also makes out-of-range ends stricter: an end that the old code silently truncated now raises `IndexDefect`. In-tree callers guard their lengths before slicing, so neither path is exercised there.

## 2) The proposition

A test checks one input. The proposition checked a law over a bounded domain. Its adopted form was:

```text
SPEC-LIBP2P-BV-SLICE
rule: external:libp2p/bytesview/slice-length-law

domain: 1 <= e <= 5, b = 1, rpos = 0
fixture: BytesView.init(@[byte 1, 2, 3, 4, 5, 6])

law:    bvSliceLenLaw1(e) == e
actual: bvSliceLenActual(e) == e - 1
```

With `b` pinned at 1, the law says the slice from relative index 1 through `e` has length `e`; the implementation produces `e - 1`. The counterexample is the smallest instance: `(b = 1, e = 4)` returns 3 bytes where the law requires 4.

The issue body was careful about the status of that law, and the care matters more than the verdict:

> The expected behavior stated in this report is INFERRED and adopted by the verifying run. The project has NOT been shown to guarantee this behavior — this report does not claim such a promise. Requirement source status: unrecorded.

That is the correct framing. Nim's `system.toOpenArray` documents inclusive bounds for sequences, but `BytesView.toOpenArray` is a separate template with its own contract. The claim was that the wrapper should follow the convention of the primitive it wraps. The maintainers agreed — eventually, and by changing the code — but at the moment of filing, the requirement was adopted rather than inherited from an upstream promise.

Authorship and authority were also separated. The proposition content was authored by the investigation agent chain; the authority to verify against it came from an explicit adoption act, a committed overlay plus a contract. The overlay's own provenance note is blunt: `Authorship confers NO authority.` An AI saying something is not auditable. An explicit adoption, a pinned subject, and a reproducible query are.

What the engine actually verifies is a model. `toOpenArray` is a template, so the carrier is constructed IR — the arithmetic of indices and lengths, not an extracted function body. The connection to the real code is the static reading of that arithmetic plus a replay harness on real bytes. This is narrower than "Axiom verified nim-libp2p," and it is the only claim the artifacts support.

## 3) The verdict

The campaign classified the result as `DISPROVED_REPRODUCIBLE`:

```json
{
  "campaign_class": "DISPROVED_REPRODUCIBLE",
  "reason": "exit 1 on both legs; all 5 guards passed; canonical digests equal",
  "accepted": true
}
```

Five guards passed on both legs:

```text
input_mismatch            pass
determinism_mismatch      pass
vacuous_blocked           pass
zero_footprint_violation  pass
environment_mismatch      pass
```

The two CI legs produced identical `canonical_digest` values:

```text
1603765c7df1c2f183e3f224d9b1fbb61ae3a1b77a1e5455cff7abea4953d14a
```

The run recorded `prove_exit: 1`, a `state_canonical_run_digest` of `29418089…`, and the toolchain:

```text
Axiom  0.6.3
Nim    2.2.10
Z3     4.13.3
Lean   4.33.0
```

`DISPROVED_REPRODUCIBLE` means that a live-generated proposition was consistently refuted in two runs and that the refutation is reproducible. It does not mean `PROVED`. The vocabulary is asymmetric on purpose: a counterexample is a finite object that can be checked; a universal correctness claim is a much stronger artifact, and the engine's supported scope does not produce one for the whole library.

## 4) What the maintainers did

The upstream timeline is short and unusually clean:

| Date (UTC) | Event |
|---|---|
| 2026-10-31 16:23 | Issue #3364 filed with the manual reproduction |
| 2026-11-13 08:23 | Update comment with the machine verification record |
| 2026-11-16 13:17 | Issue assigned to `richard-ramos` |
| 2026-11-16 13:21 | PR #3430 opened by `richard-ramos` |
| 2026-11-16 15:04 | PR merged; issue closed two seconds later |

The PR body states the contract in one paragraph:

> Make `BytesView.toOpenArray(b, e)` use inclusive bounds relative to the unconsumed data. Nonzero starts previously truncated the result: `(1, 4)` returned three bytes instead of four, and some valid single-element slices produced invalid lengths.

The fix is the one line shown above. The test change is more interesting, because the old expectation was not an accident. `BytesView` was introduced in July 2025 by PR #1497, a noise-handshake memory optimization, and the same PR added `check @(b.toOpenArray(1, 3)) == @([byte 2, 3])` — a three-wide slice asserted to have two elements. The defect was born with its own specification. For sixteen months, green CI asserted the wrong length, which is why the arithmetic could look deliberate. The fix corrected the expectation to `[2, 3, 4]`:

```diff
-    check @(b.toOpenArray(1, 3)) == @([byte 2, 3])
+    check @(b.toOpenArray(1, 3)) == @([byte 2, 3, 4])
```

and added a regression test that quantifies over every valid slice, at every consumption offset:

```nim
test "inclusive slice bounds":
  var b = BytesView.init(@[byte 1, 2, 3, 4, 5, 6])
  for consumed in 0 .. 5:
    let remaining = @(b.data())
    for first in 0 ..< b.len:
      for last in first ..< b.len:
        check @(b.toOpenArray(first, last)) == remaining[first .. last]
    b.consume(1)
```

The loop runs 56 differential checks: six consumption states, with remaining lengths from 6 down to 1, and every valid `(first, last)` pair in each. It does not cover the empty view, `e >= len`, `b > e`, or negative bounds, so the stricter out-of-range behavior is not pinned by this test. What it does pin is the contract the old expectation got wrong. This is a stronger artifact than the Axiom proposition in one decisive respect: it runs against the real function, in the project's own test suite, over the full space of valid pairs and consumption offsets, not over a five-element domain with `b` pinned at 1. It is also executable by anyone who clones the repository, with no engine, no release bundle, and no access to my infrastructure.

The maintainer wrote the fix independently. Axiom supplied the proposition, the counterexample, and the report; it did not supply the patch. That division is the contribution model working as intended.

## 5) What did not survive

The verification trail has a half-life, and this one expired faster than the code it described.

| Claim | What the record now shows |
|---|---|
| The verdict can be inspected in CI | The fork `Archright/nim-libp2p` returns 404; run `43363278211` is inaccessible |
| The verdict can be replayed from a public bundle | The instructions cite `v0.6.3` of `Archright/axiom-cli`; that repository was created on 2026-11-18, five days after the evidence document, and its releases begin at `v0.6.5` |
| A third party replayed it | The evidence document's §6 says the observation was a local cold replay on 2026-11-13; §9 labels it `third-party reproduction`, but no independent person, machine, or timestamp is named |
| The digests are identical everywhere | CI legs A and B match (`1603765c…`); local runs match each other (`9ee9d512…`); CI and local differ on `canonical_digest`. The host-independent axis is `state_canonical_run_digest`, which does match |
| The discovery was autonomous | The evidence document's §8 discloses that the prompt explicitly indicated the defect — the length law `e - 2b + 1`, the off-by-`b` — and calls the result a `guided observation, not autonomous defect discovery` |

The third row is the one I have to own. The issue comment says `reproduced again by a third-party cold replay on a clean machine`. The evidence document supports `a local cold replay following a published procedure`. Those are not the same claim. The procedure was third-party-accessible; the execution was mine. I wrote the stronger sentence, and the record does not back it.

The second row is a documentation defect rather than an overstatement about the bug. A reproduction instruction that points at a repository created five days later cannot be executed as written. The `v0.6.3` bundle, the `engine_build_id`, and the bundle hash are therefore unverifiable against any public artifact today.

The fourth row is a subtlety, not a contradiction. `canonical_digest` is environment-bound: it is deterministic inside a host configuration, and it changes when the execution configuration changes. `state_canonical_run_digest` is the host-independent reproduction axis. The evidence document states this precisely; a reader who only sees `canonical digests identical` can easily overgeneralize it.

The fifth row is the most important for how the result should be described. The campaign connected a live AI agent to a deterministic verification boundary. It did not demonstrate unguided autonomous discovery, and the document says so. The proposition named a defect the prompt had already pointed at. That is still a real pipeline result — the agent had to produce a well-formed target, spec, and description, and the engine had to refute it reproducibly — but it is not the same result as `Axiom found a bug nobody told it about`.

## 6) What this proves, and what it does not

**It proves the behavior was wrong under the adopted law.** The pre-fix template returned `e - 2b + 1` elements for a view-relative inclusive slice. The upstream maintainers reproduced the nonzero-start truncation, accepted the convention, changed the code, and added a test that compares every valid slice against ordinary sequence slicing. That is independent confirmation of the behavior, in the project's own repository.

**It does not prove the whole library.** The proposition covers one template, one length law, one pinned domain (`1 <= e <= 5`, `b = 1`, `rpos = 0`), and a constructed arithmetic model. The evidence document scopes it the same way: one EQUIPPED lane plus one unsupported claim, not a claim about all of nim-libp2p or other symbols.

**It does not prove the original function by extraction.** The template was modeled, not lifted. The correspondence between model and code is supported by static reading and by the upstream tests, not by a mechanical source-extraction certificate.

**It does not prove autonomous discovery.** The prompt guided the campaign to the defect family. The agent's contribution was the document — the correct combination of target, spec, and description — inside a deterministic boundary. That is a real contribution, but it is not the same as search without a hint.

**It does not remain independently replayable.** The run is gone, the engine version cited has no public release, and the bundle was never published at the cited path. The verdict is a documented claim, not a re-runnable one. The merged diff and test are re-runnable, and that is now the primary evidence.

## 7) Why the merged test is the artifact

A verdict is a statement about a run. A merged test is a constraint on every future run. The first can expire when a fork is deleted, a release is moved, or a document's links rot. The second is executed by the project's CI on every pull request, including the ones written by people who have never heard of Axiom.

That asymmetry is the lesson I am taking from this campaign. The most valuable output was not `DISPROVED_REPRODUCIBLE`. It was the eleven-line test that now fails if anyone reintroduces the double subtraction. The second most valuable output was the issue body's explicit statement that the requirement was inferred and adopted, not guaranteed — because that sentence is what let a maintainer evaluate the claim instead of accepting an authority.

This is also why I am publishing the decay rather than re-hosting the evidence with a fresh hash. Re-hosting would preserve the appearance of reproducibility without restoring the thing that made it reproducible: an executable path from a public artifact to a verdict. The executable path that still exists goes through the upstream repository. Pointing at it is more honest than pointing at a snapshot of my own.

There is a design consequence for Axiom. A verification record should ship with the version it cites, or it should cite only versions that already exist. It should keep the run under an identity the author controls, not a fork that can be deleted. And it should distinguish three things in its own vocabulary: a local replay, a third-party replay, and a third-party-accessible procedure. The current record conflates the first and the second in one table row.

<hr />

## 8) What the achievement was

Axiom's achievement was not `finding a bug` in the abstract. It was turning an adopted proposition about a real library into a counterexample specific enough for a maintainer to confirm, and then getting out of the way while the maintainer wrote the fix and the regression test.

That is a narrower claim than the label suggests, and a more useful one. It says the pipeline can produce a falsification that survives contact with upstream review. It does not say the pipeline can prove a library correct, discover defects without guidance, or preserve its own evidence forever. Those are separate claims, and each needs its own artifacts.

The upstream result is now part of nim-libp2p's history: a one-line correction, a test that enumerates the valid slice space, two approvals, and a merge. The Axiom run is a paragraph in an evidence document whose links no longer resolve. I know which of the two I want the work to be judged by.

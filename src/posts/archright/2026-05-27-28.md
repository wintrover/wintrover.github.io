## 1. The Strange Scene

While refactoring the quality gate, I saw something strange.

The CPU was idle.

But the system was slow,
and sometimes memory exploded.

At first, I reached for the familiar conclusion.

`waitForExit()` is the problem.
Let's make it async.
Let's manage processes with an event loop.

These days, that's a natural thought.

But the actual bottleneck wasn't the absence of async.

What I had chosen wrong wasn't the execution style.
It was the unit of parallelism itself.

## 2. I Thought It Was Parallel

The quality gate structure at the time looked like this.

```
Gate Runner
 ├─ semaphore(maxJobs)
 ├─ startProcess()
 └─ waitForExit()
```

On the surface, it looks parallel.

`maxJobs=14`

The setting exists.

So I naturally assumed multiple jobs were running simultaneously.

But they weren't.

While holding the semaphore, `waitForExit()` blocked,
freezing the entire execution flow.

The result:

```
configured parallelism = 14
actual parallelism   = 1
```

At that moment I realized.

The problem wasn't the number of threads.

The problem was what I had defined as the target of concurrent execution.

## 3. My First Proposal: Async Process Pool

My first reaction was stronger async-ification.

The design looked like this.

```
asyncdispatch
↓
AsyncProcessPool
↓
event-driven completion
↓
next scheduling
```

Launch processes non-blocking,
receive exit events, and schedule the next job.

Clean.

But as I reviewed it, problems appeared.

The level of `asyncproc`-based model I expected
didn't exist in the Nim 2.x standard library.

It was possible, but I would have had to pull
the entire event loop into the design center.

And there was a bigger problem.

Async is not a local change.

```
hook
↓
dispatcher
↓
runner
↓
gate
```

The entire call chain gets infected
by the async/await structure.

I didn't want to rebuild the entire orchestrator
just to gain parallelism.

## 4. So I Changed the Question

Is async necessary?

No.

What I actually wanted was this.

> I want to run multiple processes at the same time.

These two are different.

Processes are already scheduled by the operating system.

What I needed to do wasn't increase threads,
but simply manage the process lifecycle.

So I changed direction.

## 5. Final Choice: Synchronous Batch Flexing

The final structure became this.

```
spawn up to maxJobs
↓
poll running()
↓
free slot
↓
spawn next
```

The core principle was simple.

- Process parallelism → Delegated to OS
- Orchestration → Kept single-threaded
- Output → Directly piped to parent stream
- Only completion detection is performed

The resulting execution model:

```
Thread Count   = 1
Process Count  = N
```

The important thing here is:
I didn't remove async.

I made async unnecessary.

## 6. But Speed Wasn't the First Problem

OOM was.

I had already blown up memory twice in the quality gate.

The cause was simple.

Parallel execution count was independent of system state.

Even with 500MB of memory left,
I kept spawning new compile processes.

In the end, it wasn't parallelism.
It was a stampede.

So I redesigned the quality gate itself one last time.

## 7. How I Redesigned the Quality Gate

### 1. Process parallelism is delegated to the OS

```
single orchestrator
+
multiple child processes
```

Remove the thread pool.

Keep only process parallelism.

### 2. Concurrency is limited by memory pressure

```
spawn
↓
observe MemAvailable
↓
throttle
↓
continue
```

Don't decide parallelism by CPU count.

Dynamically limit based on remaining memory.

### 3. Failures are isolated per job unit, not system-wide

```
process limit
↓
gate failure
↓
system survives
```

A single compile failure must not cascade
into a total system failure.

## 8. My Current Selection Criteria

**Synchronous Batch Flexing**

I choose this when:

- Most tasks are external processes
- The OS scheduler is already strong enough
- Execution flow simplicity matters
- Memory predictability is important
- Output streaming is needed

Examples:

- build system
- compiler orchestration
- CI/CD
- verification engine

**Asynchronous Multithreading**

I choose this when:

- Connection count is high
- Event-driven architecture
- Latency hiding is critical
- Cancellation is needed
- Tasks themselves are IO-bound

Examples:

- websocket
- API gateway
- crawler
- realtime service

## 9. Conclusion

I used to think like this.

> If you need parallelism, add async.

Now I think like this.

> If you need parallelism, first define the scheduling target.

CPU?
Thread?
Process?

This time, it was process.

So I didn't add async.

Instead, I moved the responsibility of parallelism
to the operating system.

And the quality gate became—before it became faster—
a system that survives to the end.

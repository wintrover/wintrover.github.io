In October 2026 I ran an experiment in which a verification engine disproved a formal proposition authored by an AI agent, against a real Nim TOML parser. The agent stated a precise claim about every byte the parser can read; the claim was turned into a small mathematical statement and checked against the real program; and the verdict came back as a counterexample — one specific byte that breaks the claim.

What the process exposed was not only the refutation but a boundary between three things: what the agents authored, what the tool actually measured, and what I refused to do to make the result look cleaner than it was. This document reconstructs and reports the facts of that experiment.

<hr />

## Background: terminology

**TOML** is a plain-text format for configuration files — the `title = "hello"` kind of file that programs read when they start up. A **parser** is the program that reads such text and either accepts it or rejects it; the parser under test here is written in the Nim programming language. Which characters may appear inside a quoted string is itself a rule, and a program's rules can disagree with the official specification it claims to follow.

**Formal verification** is the alternative to testing. A test checks one example at a time: feed the parser one bad file, and if it is accepted, one bug has been found — for today. Formal verification instead turns the rule into a mathematical statement and hands it to a **solver** (here, Z3), which answers either "this holds for every possible input" or "here is a concrete input that breaks it." That breaking input is a **counterexample**, and unlike a bug report it is a proof that the claim is false.

**Axiom** is the verification engine this project builds: the machinery that takes a claim, turns it into a solver question, runs the solver, and records the verdict. An **agent** in this experiment is an AI assistant that reads code and writes analysis reports; it authored claims but did not execute code.

## 1) The subject and the candidate

The subject was [`status-im/nim-toml-serialization`](https://github.com/status-im/nim-toml-serialization) at commit `4aa8e2223649fc0837c490a4acfca7b8b1e756f9` — a real, publicly available TOML parser. The clone was read-only, and the version was pinned. `git status --porcelain` was empty before and after the run, and the module under test had a fixed hash:

```text
toml_serialization/lexer.nim
sha256 19d69eed84f74c51fa1784b2e71a4525abc8d2b8aa854c567565d2d603133f4d
```

The repository's README claims conformance to TOML v1.1.0 — the official specification. Inside `lexer.nim` (the character-reading part of the parser), the rule for a single-line basic string rejects a raw byte only when it is one of four values:

```nim
if ord(next) in {8, 16, 31, 127}:        # lexer.nim:588
  raiseInvalidChar(lex, next)
```

`{8, 16, 31, 127}` is the complete list of bytes that the string gate rejects. The multi-line string scanner uses a smaller set:

```nim
if ord(next) in {16, 31, 127}:           # lexer.nim:554
  raiseInvalidChar(lex, next)
```

The comment path in the same file already applies the full specification set:

```nim
invalidCommentChar = {'\x00'..'\x08', '\x0A'..'\x1F', '\x7F'}   # lexer.nim:75
```

`'\x00'..'\x08'` means every byte from 0 through 8, and `'\x0A'..'\x1F'` every byte from 10 through 31 — in other words, all control characters. The string gate accepts bytes that the repository's own comment gate rejects, and the README claims conformance to a specification that forbids them. That contrast is the candidate's basis; a control byte such as `0x07` (BEL) sits in the gap.

## 2) Two blind agents, seven candidates each, and one shared blind spot

I did not give the discovery agents the answer, and I did not tell them which defect family to look for. Two independently authored analysis reports read the pinned repository and produced ranked contradiction candidates — places where the code appears to contradict its own claims. Each report contained seven genuine candidates, and three converged across the two reports. Convergence of two independently performed analyses is a more reliable signal than a repetition of the same analysis.

The experiment record describes both runs as zero-context — the agents were given no background hints. No prompt transcript or invocation log is published, so that framing is documented rather than machine-attested. The countable part — seven candidates in each report, three overlaps — is in the preserved files.

Both reports missed the `\xHH` decode semantics and the BEL anchor that would later become the first counterexample. The specification pass — a separate step whose job was to turn candidates into precise claims — introduced `0x07` itself, then went back through the inherited citations and corrected four of them, including an off-by-one violation set in one report that had omitted `0x16`.

That correction is evidence that the discovery layer, the specification layer, and the verification layer were separate, and that the specification layer contradicted its inputs where the bytes required it.

The specification pass then scored eleven candidates on four criteria: whether the defect is real (the code contradicts its own claim or API contract), whether it is small enough to state as math, whether it can be replayed through the public API, and whether a known-healthy control case exists. Candidate 1 — the string control-character gate — was the only one that scored high on all four.

## 3) The proposition

The agent wrote a claim, not a test. A test checks one input; a claim covers every input at once.

```text
S2:  ∀ c ∈ D:  reject(c) = forbid(c)

D          = { c | (c ≥ 1) ∧ (c ≤ 255) ∧ (c ≠ 10) ∧ (c ≠ 13) ∧ (c ≠ 34) ∧ (c ≠ 92) }
forbid(c)  = (c ≤ 8) ∨ (c ≥ 10 ∧ c ≤ 31) ∨ (c = 127)
reject(c)  = (c = 8) ∨ (c = 16) ∨ (c = 31) ∨ (c = 127)
defect(c)  = forbid(c) ∧ ¬reject(c)
```

Each line reads as follows. `D` is the set of bytes in play — 1 through 255, with a few structural characters removed. `forbid(c)` is the rulebook: control bytes are forbidden. `reject(c)` is the program: it rejects only 8, 16, 31, and 127. `defect(c)` defines the disagreement — bytes the rulebook forbids but the program still accepts.

The domain excludes the structural exits on the grounds that they are not gate decisions: `10` (LF) and `13` (CR) terminate the single-line string, `34` (`"`) is the delimiter, and `92` (`\`) opens the escape path. `0` is excluded because `EOF* = '\0'` makes NUL an accidental rejection through the structural exit rather than a gate decision. Tab (`9`) is excluded from `forbid` because TOML permits it as whitespace inside a string.

What the pipeline actually verifies is a carrier — a small function that stands in for the claim. This carrier is a direct boolean model of the code's gate:

```nim
func d2StringGateReject*(c: int): bool =
  (c == 8) or (c == 16) or (c == 31) or (c == 127)
```

The control carrier is the repository's own comment set:

```nim
func d2CommentGateReject*(c: int): bool =
  (c <= 8) or (c >= 10 and c <= 31) or (c == 127)
```

The control is set-equal to `forbid` on the domain. If the control produced a counterexample, the fault would be in the injected specification rather than the subject. A tool that can only answer "defect" measures nothing; this differential rules out that failure mode.

## 4) Authorship and adoption

A claim authored by an AI has no authority by itself. The experiment record and the contract attribute the proposition's content to the agent chain; no prompt transcript is published, so this is documented authorship rather than independently attested authorship. The public bundle preserves the two discovery reports verbatim (they were already English); the specification and the experiment record are English translations of the Korean originals, with original hashes recorded in `TRANSLATIONS.md`. The contract states the split explicitly: **content authorship belongs to the agent chain; the authority to verify against it belongs to an explicit adoption act.**

That adoption is a committed overlay (`SPEC-TOML-D2-AGENT`) plus a product contract. The overlay pins `specOrigin: soExplicit`; the validator fails closed on anything else. The contract records why: an out-of-tree claim authored by an agent has no in-band authority in the subject repository, so the only legitimate way to verify it is to adopt it explicitly and say so.

Authorship by the agent chain and adoption are distinct. "An AI said so" is not auditable; the explicit adoption and submission of the claim is.

## 5) One run, two outcomes

The defect run was a single `ax prove` invocation against the pinned subject — one command, one verdict request:

```text
AXIOM_STATE_DIR=state_e1 \
AXIOM_PROVE_VAULT_DIR=vault_e_defect \
bin/ax prove --project env_p/subject \
  --target 'toml_serialization/lexer.nim::scanString'
```

What follows is the tool's log, quoted verbatim. First, the pipeline records that the adopted overlay entered the run:

```text
[INFO] axiom_engine: toml d2-agent overlay carriers synthesized:
d2StringGateReject (gate d2StringGateReject=@[8, 16, 31, 127]) +
d2CommentGateReject (forbid 8/10/31/127)
domain=1<=c<=255 exclusions=4 obligations=7/7 eligible=true/true
source=toml_serialization/lexer.nim
```

Within that one run, the two carriers received different outcomes:

```text
toml_serialization/lexer.nim::scanString           → clDisproved
toml_serialization/lexer.nim::d2CommentGateReject  → clProved
```

`clDisproved` means the solver found a concrete byte where the parser's gate model and the rulebook disagree. `clProved` on the control means the known-healthy carrier passed. The vault — the run's evidence store — recorded `certRed` for `scanString` and `certZ3Candidate` for the control. The BMC lane, the pipeline's solver lane, reached a definite SAT — "a counterexample exists, and here is a model":

```text
[ERROR] loop_driver: IR pipeline FAIL: scanString
status=psFail provenance=solverMethod=smBMC,provenance=pkNone
```

The run accounting then failed closed:

```text
[WARN] axiom_engine: canonical run accounting:
contestedCount=0 ∨ unsatisfiedCount=1 ⇒ GateVerdict=FAIL
```

"Failed closed" means the run records itself as a failure whenever anything is unresolved or unsatisfied. One unsatisfied obligation made the whole verdict `GateVerdict=FAIL`.

The cold rerun is the determinism check: the `canonicalRunDigest` — a fingerprint of the run's content — was identical across the first run and the cold run:

```text
3516fcfcb4d891f99caed95d55405e29a8032371b5ba73028dee03e598cced6a
```

The `.err` files differed by exactly one line — the vault path. The timing fields inside the proof state did not match, so the precise statement is "identical canonical digest," not "byte-identical runs."

One limitation was observed the same day: the control carrier could not be targeted standalone. A direct `--target d2CommentGateReject` was refused with `NotFound`: the control was reachable only as a dependency of the defect run, not as an entry point of its own. The control verdict was therefore observed **inside the same run**, which is the only place the differential exists. That limitation was later removed (see below).

## 6) The gap: when the verifier blocks its own counterexample

The Phase E run above ended with a disproof, not a replay: the counterexample was found but never re-run against the real parser. That was the pre-fix state.

The solver lane had a SAT model: a concrete counterexample candidate. The pipeline's P4 re-validation step is supposed to check that candidate before promoting it. For a boolean-returning carrier, it did the opposite: it read the carrier's `result` binding as a bare precondition and asserted the carrier body — treating "this byte is rejected" as an assumption instead of a question.

```smt2
(declare-const c (_ BitVec 64))
(declare-const result Bool)
(assert (and (= c c)
  (or (or (or (= c #x0000000000000008)
              (= c #x0000000000000010))
          (= c #x000000000000001F))
      (= c #x000000000000007F))))
(assert (not (= <gate(c)> <forbid(c)>)))
(check-sat)
```

The first `assert` forces `c` into `{8, 16, 31, 127}` — the set of bytes where the defect does not exist. The query returned `unsat`; the validator marked the counterexample `cvSpurious` (a false alarm); the candidate was preserved, `vsDisproved` was never reached, and the replay trigger never fired.

The root cause was in the generic pipeline, not in the binding. The boolean branch had landed earlier in `05055aab5`; every previous carrier had a non-boolean body (`length mod 8`, `1 + code div 128`, a sizing constant), so the equality branch had always been taken and the defect had never been exposed. `p0d2g` was the first bool-returning carrier.

I did not fix it inside the experiment.

The slice's rule was explicit: if the root cause is in generic pipeline code, document it and stop. Reshaping the carrier into a `0/1` bitvector would have made the P4 pass, but it would have changed the adopted claim's meaning and left the generic defect in place for the next boolean claim. That is patch-to-pass — changing the question so the tool says "pass." The gap document's header reads `Status: NOT FIXED`, and the experiment record states that the slice did not modify any tracked file.

The fix landed later, in the generic validator, with a shape-based discriminator rather than a type-based special case: exactly one transition, a nil guard, an empty parallel update, and `resultStateName == some("result")` select the equality reading. The commit that made the change records that the defect carrier's previously unreachable branch became live, and that the post-fix run bound `c=24` and replay-agreed on the pristine decoder. Two further harness fixes followed — explicit nimble dependency roots for the stamped harness, and include-splicing plus subject-repository binding for collateral kernels — both infrastructure around the run, not changes to the adopted claim.

The original experiment record was frozen before those fixes. It still says the expected verdict is `ACCEPTANCE: INCOMPLETE`. That is accurate for the state the record describes; the follow-up commits are published alongside it rather than rewriting the record.

On 2026-10-20, after those fixes landed, I re-ran the full harness against Axiom HEAD `7ae9561a9` with a rebuilt `bin/ax` v0.5.9. Both the defect leg and the cold rerun produced:

```text
[INFO] ir_pipeline_runner: [ce-replay] d2StringGateReject — replay agreed;
BUG_FOUND payload assembled (13 records)
```

`C1–C5`, the run's five acceptance conditions, were all observed (`OBS`); the canonical digest matched the recorded `3516fcfc…` in both legs; and the harness printed `ACCEPTANCE: PASS`. The frozen record still says `INCOMPLETE`; that is its contemporaneous expectation, not the final observation. The run log and state artifacts are published in the public evidence snapshot rather than committed to the Axiom tree.

## 7) What this does not prove

Stating without qualification that "Axiom found a bug" overstates the result: the solver refuted a constructed model, the correspondence to the original code is supported by static analysis and subsequent replay rather than full source extraction, and this is a conformance discrepancy — a rulebook-compliance gap — rather than a security-vulnerability claim.

**The solver verified a model, not the original function.** The carriers are constructed IR — a simplified model of the code. The original gates are stream-coupled (their logic is intertwined with reading bytes from the input stream), so they were deliberately not carried as bodies. The canonical seal — the mechanism that would certify the model as mechanically extracted from the source — declined with `EA_UNSUPPORTED: ckVarTy`. That is the accurate verdict when the extraction boundary cannot be measured. The SAT/UNSAT results are about the adopted model. The correspondence between that model and the original is supported by static reading of the loop structure, the UTF-8 table, and the comment set, and by the post-fix replay observation on the pristine decoder. It is not a formal proof of general correspondence.

**The end-to-end observation is later than the frozen record.** The frozen experiment record's expected verdict is `INCOMPLETE (replay/promotion unavailable — P4 bool-binding pipeline gap)`. On 2026-10-20, a post-fix run on Axiom HEAD `7ae9561a9` with a rebuilt v0.5.9 binary observed C1–C5 all `OBS` and `ACCEPTANCE: PASS`; the log and state artifacts are published in the public evidence snapshot, not committed in the Axiom tree. The PASS is an observation of the harness on that build, not a rewrite of the frozen record.

**This is not a vulnerability report.** There is no CVE, no CVSS score, no severity claim, and no upstream advisory. The scope is a TOML conformance gap in a string content gate. The multi-line gate at `:554` is an auxiliary counterexample family, not part of the primary model. Discovery completeness is not claimed: the two reports missed the BEL anchor, and nothing here proves that no other defect exists.

The witness byte requires the same care. The committed Phase E log shows the SAT failure but does not print the model's byte. `c=24` (0x18) appears in the probe capture quoted in the gap document and in the post-fix commit message. The contract commits the witness **set** — every `forbid` member outside `{8, 16, 31, 127}` — not z3's particular choice. `c=24` is the solver's model in the recorded probe and post-fix run, not a byte printed by the original Phase E log.

## 8) Why publish the failure

The gap was the more valuable result of this experiment. A verification system that publishes only the runs where it passes does not demonstrate its verification ability.

The useful artifact is the trajectory: two blind candidate pools, a specification that corrected its inputs, an explicit adoption act, a differential that put a disproof and a proof in the same run, a pipeline bug that blocked its own counterexample, a refusal to reshape the claim to pass, a later generic fix that did not touch the binding, and a post-fix run where the original decoder's replay agreed.

Each step of the trajectory is backed by the public evidence bundle: the two discovery reports verbatim, the agent-authored specification and the frozen experiment record in English translation (original hashes in `TRANSLATIONS.md`), the gap document, the run logs, the vault manifest, the trajectory (with local paths redacted), the cold-run proof states, and the commit messages of the follow-up fixes.

The bundle is a curated snapshot rather than a link into the origin. Its `SHA256SUMS` proves that the public bytes have not changed; it cannot prove that the snapshot equals the origin, or that the run happened. The README says so explicitly. The subject side is public and pinned. The commands below pin and verify the source; they do not by themselves run the decoder. The public evidence README also includes a one-file API probe:

```nim
import toml_serialization

discard Toml.decode("k = \"a\x07b\"", TomlValueRef)  # accepted by lexer.nim:588
```

In that probe, `\x07` is a Nim hexadecimal byte escape: the TOML document contains a raw BEL byte (0x07), not the four characters `\x07` and not a TOML escape sequence. TOML v1.1.0 also permits an escaped `\x07` inside a basic string; the counterexample is specifically a raw, unescaped control byte.

```sh
git clone https://github.com/status-im/nim-toml-serialization
git -C nim-toml-serialization checkout 4aa8e2223649fc0837c490a4acfca7b8b1e756f9
sha256sum nim-toml-serialization/toml_serialization/lexer.nim
```

The question this experiment tested was whether the system could allow the agent's claim to fail and keep the failure intact.

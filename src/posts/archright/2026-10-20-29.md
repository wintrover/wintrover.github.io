Can an AI agent write a formal claim that a verifier actually refutes?

Not "an agent suggested a bug." Not "a model wrote a proof-shaped paragraph." The stronger version: an agent authors a proposition with a domain, a precondition, and a postcondition; a separate verification pipeline adopts it; a solver decides it; and the decision is allowed to come back negative.

In October 2026 we ran that experiment against a real Nim TOML parser. The refutation was interesting. The more useful result was the boundary it exposed: between what the agents authored, what the tool actually measured, and what we refused to do to make the result look cleaner than it was.

This is the record of that boundary.

<hr />

## 1) The subject and the candidate

The subject was [`status-im/nim-toml-serialization`](https://github.com/status-im/nim-toml-serialization) at commit `4aa8e2223649fc0837c490a4acfca7b8b1e756f9`. The clone was read-only. `git status --porcelain` was empty before and after the run, and the module under test had a fixed hash:

```text
toml_serialization/lexer.nim
sha256 19d69eed84f74c51fa1784b2e71a4525abc8d2b8aa854c567565d2d603133f4d
```

The repository's README claims TOML v1.1.0 conformance. Inside `lexer.nim`, the single-line basic-string scanner rejects a raw byte only when it is one of four values:

```nim
if ord(next) in {8, 16, 31, 127}:        # lexer.nim:588
  raiseInvalidChar(lex, next)
```

The multi-line scanner uses an even smaller set:

```nim
if ord(next) in {16, 31, 127}:           # lexer.nim:554
  raiseInvalidChar(lex, next)
```

But the same file already contains the full set on the comment path:

```nim
invalidCommentChar = {'\x00'..'\x08', '\x0A'..'\x1F', '\x7F'}   # lexer.nim:75
```

That contrast is the whole candidate: the string gate accepts bytes that the repository's own comment gate rejects, and the README claims conformance to a specification that forbids them. A byte such as `0x07` (BEL) sits in the gap.

<hr />

## 2) Two blind agents, seven candidates each, and one shared blind spot

We did not give the discovery agents the answer. We did not even tell them which defect family to look for. Two independently authored analysis reports read the pinned repository and produced ranked contradiction candidates. Each produced seven genuine candidates. Three converged across the two reports.

The experiment record describes both runs as zero-context. No prompt transcript or invocation log is published, so that framing is documented rather than machine-attested. The countable part — seven candidates in each report, three overlaps — is in the preserved files.

The honest part is what they missed.

Both agents failed to identify the `\xHH` decode semantics and the specific BEL anchor that would later become the first counterexample. The spec-inference agent introduced `0x07` itself, then went back through the inherited citations and corrected four of them — including an off-by-one violation set in one report that had omitted `0x16`.

That correction is not a footnote. It is evidence that the chain was not a single model agreeing with itself. The discovery layer, the specification layer, and the verification layer were separate, and the specification layer contradicted its inputs where the bytes required it.

The spec agent then scored eleven candidates on four criteria: whether the defect is real (code contradicts its own claim or API contract), whether it is formalizable on a small domain, whether it can be replayed through the public API, and whether a differential control exists. Candidate 1 — the string control-character gate — was the only one that scored high on all four.

<hr />

## 3) The proposition

The agent did not write a test. It wrote a claim:

```text
S2:  ∀ c ∈ D:  reject(c) = forbid(c)

D          = { c | (c ≥ 1) ∧ (c ≤ 255) ∧ (c ≠ 10) ∧ (c ≠ 13) ∧ (c ≠ 34) ∧ (c ≠ 92) }
forbid(c)  = (c ≤ 8) ∨ (c ≥ 10 ∧ c ≤ 31) ∨ (c = 127)
reject(c)  = (c = 8) ∨ (c = 16) ∨ (c = 31) ∨ (c = 127)
defect(c)  = forbid(c) ∧ ¬reject(c)
```

The domain excludes the structural exits rather than pretending they are gate members: `10` (LF) and `13` (CR) terminate the single-line string, `34` (`"`) is the delimiter, and `92` (`\`) opens the escape path. `0` is excluded because `EOF* = '\0'` makes NUL an accidental rejection path through the structural exit, not a gate decision. Tab (`9`) is excluded from `forbid` because TOML permits it as whitespace inside a string.

The carrier the pipeline would verify is a direct boolean model of the code's gate:

```nim
func d2StringGateReject*(c: int): bool =
  (c == 8) or (c == 16) or (c == 31) or (c == 127)
```

The control carrier is the repository's own comment set:

```nim
func d2CommentGateReject*(c: int): bool =
  (c <= 8) or (c >= 10 and c <= 31) or (c == 127)
```

The control is set-equal to `forbid` on the domain. If the control ever produced a counterexample, the fault would be in the injected specification, not in the subject. That is the differential's guard against self-deception.

<hr />

## 4) Who is allowed to say this is true?

This is the part that is easy to skip, and it is the part that makes the rest meaningful.

The experiment record and the contract attribute the proposition's content to the agent chain. No prompt transcript is published, so this is documented authorship rather than independently attested authorship. The specification file preserves the two discovery reports verbatim, and the contract states the split explicitly: **content authorship belongs to the agent chain; the authority to verify against it belongs to an explicit adoption act.**

That adoption is a committed overlay (`SPEC-TOML-D2-AGENT`) plus a product contract. The overlay pins `specOrigin: soExplicit`; the validator fails closed on anything else. The contract records why: an out-of-tree claim authored by an agent has no in-band authority in the subject repository, so the only legitimate way to verify it is to adopt it explicitly and say so.

This distinction is the difference between "an AI said so" and "we adopted a claim and submitted it to a verifier." The second is auditable. The first is not.

## 5) One run, two outcomes

The defect run was a single `ax prove` invocation against the pinned subject:

```text
AXIOM_STATE_DIR=state_e1 \
AXIOM_PROVE_VAULT_DIR=vault_e_defect \
bin/ax prove --project env_p/subject \
  --target 'toml_serialization/lexer.nim::scanString'
```

The pipeline's own log records that the adopted overlay really entered the run:

```text
[INFO] axiom_engine: toml d2-agent overlay carriers synthesized:
d2StringGateReject (gate d2StringGateReject=@[8, 16, 31, 127]) +
d2CommentGateReject (forbid 8/10/31/127)
domain=1<=c<=255 exclusions=4 obligations=7/7 eligible=true/true
source=toml_serialization/lexer.nim
```

Inside that run, the two carriers received different outcomes:

```text
toml_serialization/lexer.nim::scanString           → clDisproved
toml_serialization/lexer.nim::d2CommentGateReject  → clProved
```

The vault recorded `certRed` for `scanString` and `certZ3Candidate` for the control. The BMC lane reached SAT, not a timeout and not an inconclusive result:

```text
[ERROR] loop_driver: IR pipeline FAIL: scanString
status=psFail provenance=solverMethod=smBMC,provenance=pkNone
```

The run accounting then failed closed:

```text
[WARN] axiom_engine: canonical run accounting:
contestedCount=0 ∨ unsatisfiedCount=1 ⇒ GateVerdict=FAIL
```

The cold rerun is the determinism check that matters: the `canonicalRunDigest` was identical across the first run and the cold run:

```text
3516fcfcb4d891f99caed95d55405e29a8032371b5ba73028dee03e598cced6a
```

The `.err` files differed by exactly one line — the vault path. The timing fields inside the proof state did not match, so the correct statement is "identical canonical digest," not "byte-identical runs."

One more observation from that day: the control carrier could not be targeted standalone. A direct `--target d2CommentGateReject` was refused with `NotFound` from the frontier, because the carrier was reachable only through the defect run's dependency closure. The control verdict was therefore observed **inside the same run**, which is the only place the differential exists. That limitation was later removed; more on that below.

## 6) The gap: when the verifier blocks its own counterexample

The Phase E run above ended with a disproof. It did not end with a replay; that was the pre-fix state.

The BMC lane had a SAT model. The pipeline's P4 re-validation step is supposed to check that model before promoting it. For a boolean-returning carrier, it did the opposite. It read the carrier's `result` binding as a bare precondition and asserted the carrier body:

```smt2
(declare-const c (_ BitVec 64))
(declare-const result Bool)
(assert (and (= c c)
  (or (or (or (= c #x0000000000000008)
              (= c #x0000000000000010))
          (= c #x000000000000001F))
      (= c #x000000000000007F))))
(assert (not (= <gate(c)> <forbid(c)>)))
(check-sat)
```

The first assertion already forces `c` into `{8, 16, 31, 127}`. That is exactly the set of bytes the defect does **not** live in. The P4 query returned `unsat`, the validator marked the counterexample `cvSpurious`, the candidate was preserved, `vsDisproved` was never reached, and the replay trigger never fired.

This was a generic pipeline bug, not a bug in the binding. The boolean branch had landed earlier in `05055aab5`; every previous carrier had a non-boolean body (`length mod 8`, `1 + code div 128`, a sizing constant), so the equality branch had always been taken and the defect had never been exposed. `p0d2g` was the first bool-returning carrier.

We did not fix it inside the experiment.

The slice's rule was explicit: if the root cause is in generic pipeline code, document it and stop. Reshaping the carrier into a `0/1` bitvector would have made the P4 pass, but it would have changed the adopted claim's meaning and left the generic defect armed for the next boolean claim. That is patch-to-pass. The record says, in the gap document's own header, `Status: NOT FIXED`, and the experiment record says the slice did not modify any tracked file.

The fix landed later, in the generic validator, with a shape-based discriminator rather than a type-based special case: exactly one transition, a nil guard, an empty parallel update, and `resultStateName == some("result")` select the equality reading. The commit that made the change records that the defect carrier's previously unreachable branch became live, and that the post-fix run bound `c=24` and replay-agreed on the pristine decoder. Two further harness fixes followed: explicit nimble dependency roots for the stamped harness, and include-splicing plus subject-repository binding for collateral kernels.

The original experiment record was frozen before those fixes. It still says the expected verdict is `ACCEPTANCE: INCOMPLETE`. That is accurate for the record it describes. The follow-up commits are published alongside it rather than rewriting the record.

On 2026-10-20, after those fixes landed, we re-ran the full harness against Axiom HEAD `7ae9561a9` with a rebuilt `bin/ax` v0.5.9. Both the defect leg and the cold rerun produced:

```text
[INFO] ir_pipeline_runner: [ce-replay] d2StringGateReject — replay agreed;
BUG_FOUND payload assembled (13 records)
```

C1–C5 were all `OBS`, the canonical digest matched the recorded `3516fcfc…` in both legs, and the harness printed `ACCEPTANCE: PASS`. The frozen record still says `INCOMPLETE`; that is its contemporaneous expectation, not the final observation. The run log and state artifacts are published in the public evidence snapshot rather than committed to the Axiom tree.

## 7) What this does not prove

The temptation is to end with "Axiom found a bug." That sentence would be false in three different ways.

**The solver verified a model, not the original function.** The carriers are constructed IR: the original gates are stream-coupled and were deliberately not carried as bodies. The canonical seal declined with `EA_UNSUPPORTED: ckVarTy`, which is the honest answer when the extraction boundary cannot be measured. The SAT/UNSAT results are about the adopted model. The correspondence between that model and the original is supported by static reading of the loop structure, the UTF-8 table, and the comment set — not by a formal proof.

**The Axiom repository does not commit run outputs.** The frozen experiment record's expected verdict is `INCOMPLETE (replay/promotion unavailable — P4 bool-binding pipeline gap)`. On 2026-10-20, a post-fix run on Axiom HEAD `7ae9561a9` with a rebuilt v0.5.9 binary observed C1–C5 all `OBS` and `ACCEPTANCE: PASS`; the log and state artifacts are published in the public evidence snapshot, not committed in the Axiom tree. The PASS is an observation of the harness on that build, not a rewrite of the frozen record.

**This is not a vulnerability report.** There is no CVE, no CVSS score, no severity claim, and no upstream advisory. The scope is a TOML conformance gap in a string content gate. The multi-line gate at `:554` is an auxiliary counterexample family, not part of the primary model. Discovery completeness is not claimed: the two reports missed the BEL anchor, and nothing here proves that no other defect exists.

The witness byte deserves the same care. The committed Phase E log shows the SAT failure but does not print the model's byte. `c=24` (0x18) appears in the probe capture quoted in the gap document and in the post-fix commit message. The contract commits the witness **set** — every `forbid` member outside `{8, 16, 31, 127}` — not z3's particular choice. A reader should treat `c=24` as the solver's model in the recorded probe/post-fix run, not as a byte printed by the original Phase E log.

<hr />

## 8) Why publish the failure

The refutation is a result. The gap is a better result.

A verification system that only publishes the runs where it looks correct is not a verification system; it is a presentation layer. The useful artifact here is the trajectory: two blind candidate pools, a specification that corrected its inputs, an explicit adoption act, a differential that put a disproof and a proof in the same run, a pipeline bug that blocked its own counterexample, a refusal to reshape the claim to pass, a later generic fix that did not touch the binding, and a post-fix run where the original decoder's replay finally agreed.

None of that requires the reader to trust the narrator. The public evidence bundle contains the two discovery reports verbatim, the agent-authored specification, the frozen experiment record, the gap document, the run logs, the vault manifest, the trajectory (with local paths redacted), the cold-run proof states, and the commit messages of the follow-up fixes.

Because the Axiom repository is private, the bundle is a curated snapshot rather than a link into the origin. Its `SHA256SUMS` proves that the public bytes have not changed; it cannot prove that the snapshot equals the private origin, or that the run happened. The README says so explicitly. The subject side is public and pinned, so anyone can reproduce the decoder behavior:

```sh
git clone https://github.com/status-im/nim-toml-serialization
git -C nim-toml-serialization checkout 4aa8e2223649fc0837c490a4acfca7b8b1e756f9
sha256sum nim-toml-serialization/toml_serialization/lexer.nim
```

The interesting question was never whether an agent could produce a plausible claim. It was whether the system could let the claim fail, in public, with the failure intact.

That is the part worth keeping.

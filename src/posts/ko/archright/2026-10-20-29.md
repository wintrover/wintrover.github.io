AI 에이전트가 작성한 정형명제를 검증기가 실제로 반증할 수 있는가?

"에이전트가 버그를 제안했다"가 아니다. "모델이 증명처럼 보이는 문단을 썼다"도 아니다. 더 강한 버전은 이것이다. 에이전트가 정의역·전건·후건을 갖춘 명제를 작성하고, 별도의 검증 파이프라인이 그것을 채택하며, 솔버가 판정하고, 그 판정이 부정으로 돌아오는 것을 허용하는 것.

2026년 10월, 우리는 실제 Nim TOML 파서를 대상으로 이 실험을 했다. 반증 자체도 흥미로웠지만, 더 유용했던 것은 그 과정에서 드러난 경계였다. 에이전트가 작성한 것, 도구가 실제로 측정한 것, 그리고 결과를 더 깔끔하게 보이게 만들기 위해 우리가 하지 않기로 한 것 사이의 경계.

이 글은 그 경계의 기록이다.

## 1) 주체와 후보

주체는 [`status-im/nim-toml-serialization`](https://github.com/status-im/nim-toml-serialization)의 커밋 `4aa8e2223649fc0837c490a4acfca7b8b1e756f9`였다. 클론은 읽기 전용이었고, 실행 전후 `git status --porcelain`은 비어 있었으며, 대상 모듈의 해시는 고정돼 있었다.

```text
toml_serialization/lexer.nim
sha256 19d69eed84f74c51fa1784b2e71a4525abc8d2b8aa854c567565d2d603133f4d
```

저장소의 README는 TOML v1.1.0 부합을 주장한다. `lexer.nim` 안에서 단일행 기본 문자열 스캐너는 원시 바이트가 다음 네 값 중 하나일 때만 거부한다.

```nim
if ord(next) in {8, 16, 31, 127}:        # lexer.nim:588
  raiseInvalidChar(lex, next)
```

멀티라인 스캐너는 더 작은 집합을 쓴다.

```nim
if ord(next) in {16, 31, 127}:           # lexer.nim:554
  raiseInvalidChar(lex, next)
```

그런데 같은 파일의 주석 경로에는 이미 전체 집합이 있다.

```nim
invalidCommentChar = {'\x00'..'\x08', '\x0A'..'\x1F', '\x7F'}   # lexer.nim:75
```

이 대비가 후보의 전부다. 문자열 게이트는 저장소 자신의 주석 게이트가 거부하는 바이트를 받아들이고, README는 그 바이트를 금지하는 명세에 부합한다고 주장한다. `0x07`(BEL) 같은 바이트가 그 갭에 놓인다.

## 2) 블라인드 에이전트 둘, 각 7개 후보, 그리고 공통된 사각지대

우리는 탐색 에이전트에게 답을 주지 않았다. 어떤 결함 계열을 찾아야 하는지도 알려주지 않았다. 독립적으로 작성된 두 분석 보고서가 고정된 저장소를 읽고 순위가 매겨진 모순 후보를 냈다. 각각 7개의 진짜 후보를 냈고, 두 보고서 사이에서 3개가 수렴했다.

실험 기록은 두 실행을 제로 컨텍스트라고 서술한다. 프롬프트 원문이나 호출 로그는 공개되지 않았으므로, 그 표현은 문서화된 것이지 기계적으로 입증된 것은 아니다. 셀 수 있는 부분 — 각 보고서의 후보 7개, 3개의 중복 — 은 보존된 파일에 있다.

정직한 부분은 그들이 놓친 것이다.

두 보고서 모두 `\xHH` 디코드 의미론과, 나중에 첫 반례가 될 BEL 앵커를 찾지 못했다. 명제 합성 패스가 `0x07`을 직접 도입했고, 그다음 상속된 인용을 다시 훑으며 4건을 정정했다. 한 보고서의 위반 집합이 `0x16`을 누락한 오프바이원도 그중 하나다.

이 정정은 각주가 아니다. 체인이 한 모델이 자기 자신과 동의한 것이 아니라는 증거다. 탐색 계층, 명세 계층, 검증 계층은 분리돼 있었고, 명세 계층은 바이트가 요구하는 지점에서 입력과 자기 자신을 반박했다.

보존된 명세에 따르면, 합성 패스는 11개 후보를 네 기준으로 채점했다. 결함이 실제인가(코드가 자신의 주장이나 API 계약을 위반하는가), 작은 정의역에서 형식화 가능한가, 공개 API로 재생 가능한가, 차동 대조가 존재하는가. 후보 1 — 문자열 제어문자 게이트 — 만이 네 기준 모두에서 높은 점수를 받았다.

## 3) 명제

에이전트는 테스트를 쓰지 않았다. 주장을 썼다.

```text
S2:  ∀ c ∈ D:  reject(c) = forbid(c)

D          = { c | (c ≥ 1) ∧ (c ≤ 255) ∧ (c ≠ 10) ∧ (c ≠ 13) ∧ (c ≠ 34) ∧ (c ≠ 92) }
forbid(c)  = (c ≤ 8) ∨ (c ≥ 10 ∧ c ≤ 31) ∨ (c = 127)
reject(c)  = (c = 8) ∨ (c = 16) ∨ (c = 31) ∨ (c = 127)
defect(c)  = forbid(c) ∧ ¬reject(c)
```

정의역은 구조적 종료를 게이트 멤버인 척하지 않고 배제한다. `10`(LF)과 `13`(CR)은 단일행 문자열을 종료시키고, `34`(`"`)는 구분자이며, `92`(`\`)는 이스케이프 경로를 연다. `0`은 `EOF* = '\0'` 때문에 NUL이 구조적 종료를 통해 우연히 거부되는 경로라 게이트 판정이 아니므로 배제했다. 탭(`9`)은 TOML이 문자열 내부 공백으로 허용하므로 `forbid`에서 제외된다.

파이프라인이 검증할 캐리어는 코드 게이트의 직접적인 불리언 모델이다.

```nim
func d2StringGateReject*(c: int): bool =
  (c == 8) or (c == 16) or (c == 31) or (c == 127)
```

대조 캐리어는 저장소 자신의 주석 집합이다.

```nim
func d2CommentGateReject*(c: int): bool =
  (c <= 8) or (c >= 10 and c <= 31) or (c == 127)
```

대조는 정의역 위에서 `forbid`와 집합동일하다. 만약 대조에서 반례가 나왔다면, 결함은 주체가 아니라 주입된 명세에 있었을 것이다. 이것이 차동 구도가 자기기만을 막는 장치다.

## 4) 누가 이것이 참이라고 말할 수 있는가

여기가 건너뛰기 쉬운 부분이고, 나머지를 의미 있게 만드는 부분이다.

실험 기록과 계약은 명제의 내용을 에이전트 체인에 귀속한다. 프롬프트 원문은 공개되지 않았으므로, 이것은 문서화된 저작이지 독립적으로 입증된 저작은 아니다. 명세 파일은 두 탐색 보고서를 원문 그대로 보존하고, 계약은 분리를 명시한다. **내용의 저작은 에이전트 체인에, 그것을 검증할 권한은 명시적 채택 행위에 속한다.**

그 채택은 커밋된 오버레이(`SPEC-TOML-D2-AGENT`)와 제품 계약이다. 오버레이는 `specOrigin: soExplicit`를 고정하고, 검증기는 다른 값에 fail-closed한다. 계약은 이유를 기록한다. 에이전트가 작성한 트리 밖 주장은 주체 저장소 안에 권위를 갖지 않으므로, 유일하게 정당한 검증 경로는 그것을 명시적으로 채택하고 그 사실을 밝히는 것이다.

이 구분이 "AI가 그렇게 말했다"와 "우리가 주장을 채택해 검증기에 제출했다"의 차이다. 두 번째만 감사 가능하다.

## 5) 한 런, 두 결과

결함 런은 고정된 주체에 대한 단일 `ax prove` 호출이었다.

```text
AXIOM_STATE_DIR=state_e1 \
AXIOM_PROVE_VAULT_DIR=vault_e_defect \
bin/ax prove --project env_p/subject \
  --target 'toml_serialization/lexer.nim::scanString'
```

파이프라인 로그는 채택된 오버레이가 실제로 런에 들어갔음을 기록한다.

```text
[INFO] axiom_engine: toml d2-agent overlay carriers synthesized:
d2StringGateReject (gate d2StringGateReject=@[8, 16, 31, 127]) +
d2CommentGateReject (forbid 8/10/31/127)
domain=1<=c<=255 exclusions=4 obligations=7/7 eligible=true/true
source=toml_serialization/lexer.nim
```

그 런 안에서 두 캐리어는 다른 결과를 받았다.

```text
toml_serialization/lexer.nim::scanString           → clDisproved
toml_serialization/lexer.nim::d2CommentGateReject  → clProved
```

볼트는 `scanString`에 `certRed`, 대조에 `certZ3Candidate`를 기록했다. BMC 레인은 타임아웃도, 불확정도 아닌 SAT에 도달했다.

```text
[ERROR] loop_driver: IR pipeline FAIL: scanString
status=psFail provenance=solverMethod=smBMC,provenance=pkNone
```

그다음 런 회계는 fail-closed로 실패했다.

```text
[WARN] axiom_engine: canonical run accounting:
contestedCount=0 ∨ unsatisfiedCount=1 ⇒ GateVerdict=FAIL
```

콜드 재실행은 중요한 결정론 검사다. 첫 런과 콜드 런의 `canonicalRunDigest`가 동일했다.

```text
3516fcfcb4d891f99caed95d55405e29a8032371b5ba73028dee03e598cced6a
```

`.err` 파일은 정확히 한 줄 — 볼트 경로 — 만 달랐다. 증명 상태 내부의 타이밍 필드는 일치하지 않았으므로, 정확한 표현은 "동일한 canonical digest"이지 "바이트 동일 런"이 아니다.

그날의 관측이 하나 더 있다. 대조 캐리어는 단독 타깃이 될 수 없었다. `--target d2CommentGateReject` 직접 실행은 프론티어에서 `NotFound`로 거부됐다. 캐리어가 결함 런의 의존성 폐쇄를 통해서만 도달 가능했기 때문이다. 그래서 대조 판정은 **같은 런 안에서** 관측됐고, 차동이 존재하는 곳도 거기뿐이었다. 이 제한은 나중에 제거됐다.

## 6) 갭: 검증기가 자기 반례를 막을 때

위의 Phase E 런은 반증으로 끝났다. 재생으로 끝나지는 않았다. 그것이 수리 전 상태였다.

BMC 레인에는 SAT 모델이 있었다. 파이프라인의 P4 재검증 단계는 그 모델을 승격하기 전에 확인해야 한다. 불리언 반환 캐리어에서 그것은 정반대를 했다. 캐리어의 `result` 바인딩을 조건으로 읽고, 캐리어 본문을 전건으로 assert했다.

```smt2
(declare-const c (_ BitVec 64))
(declare-const result Bool)
(assert (and (= c c)
  (or (or (or (= c #x0000000000000008)
              (= c #x0000000000000010))
          (= c #x000000000000001F))
      (= c #x000000000000007F))))
(assert (not (= <gate(c)> <forbid(c)>)))
(check-sat)
```

첫 assert가 이미 `c`를 `{8, 16, 31, 127}`로 강제한다. 그것은 결함이 살지 **않는** 바이트 집합이다. P4 질의는 `unsat`을 반환했고, 검증기는 반례를 `cvSpurious`로 표시했고, 후보는 보존됐고, `vsDisproved`에 도달하지 못했고, 재생 트리거는 발화하지 않았다.

이것은 바인딩의 버그가 아니라 제너릭 파이프라인의 버그였다. 불리언 분기는 더 이른 커밋 `05055aab5`에서 들어왔고, 이전의 모든 캐리어는 비불리언 본문(`length mod 8`, `1 + code div 128`, sizing 상수)이어서 항상 등식 분기를 탔고, 결함은 드러나지 않았다. `p0d2g`가 첫 불리언 반환 캐리어였다.

우리는 실험 안에서 그것을 고치지 않았다.

슬라이스의 규칙은 명시적이었다. 근원이 제너릭 파이프라인 코드에 있으면 기록하고 멈춘다. 캐리어를 `0/1` 비트벡터로 바꾸면 P4는 통과했겠지만, 채택된 주장의 의미가 바뀌고 제너릭 결함은 다음 불리언 주장을 위해 무장된 채 남는다. 그것이 patch-to-pass다. 갭 문서의 헤더는 `Status: NOT FIXED`라고 적고 있고, 실험 기록은 슬라이스가 추적 파일을 수정하지 않았다고 말한다.

수리는 나중에 제너릭 검증기에서 이뤄졌다. 타입 기반 특례가 아니라 형태 기반 판별자 — 정확히 하나의 전이, nil 가드, 빈 병렬 업데이트, `resultStateName == some("result")` — 가 등식 판독을 선택한다. 그 변경 커밋은 결함 캐리어의 이전에는 도달 불가능했던 분기가 살아났고, 수리 후 런이 `c=24`를 바인딩해 원본 디코더에서 재생 합의했다고 기록한다. 이후 하네스 수리 두 건이 뒤따랐다. 스탬프된 하네스의 명시적 nimble 의존성 루트, 그리고 콜래트럴 커널을 위한 include-splice와 주체 저장소 바인딩이다.

원래 실험 기록은 그 수리들 전에 동결됐다. 여전히 예상 판정을 `ACCEPTANCE: INCOMPLETE`라고 적는다. 그것은 그 기록이 서술하는 상태에 대해서는 정확하다. 후속 커밋은 기록을 다시 쓰는 대신 나란히 공개된다.

2026-10-20, 그 수리들이 착지한 뒤 우리는 Axiom HEAD `7ae9561a9`와 재빌드한 `bin/ax` v0.5.9로 전체 하네스를 다시 실행했다. 결함 레그와 콜드 재실행 모두에서 다음 줄이 나왔다.

```text
[INFO] ir_pipeline_runner: [ce-replay] d2StringGateReject — replay agreed;
BUG_FOUND payload assembled (13 records)
```

C1–C5가 모두 `OBS`였고, canonical digest는 두 레그 모두 기록된 `3516fcfc…`와 일치했으며, 하네스는 `ACCEPTANCE: PASS`를 출력했다. 동결된 기록은 여전히 `INCOMPLETE`라고 적는데, 그것은 그 당시의 예상이지 최종 관측이 아니다. 실행 로그와 상태 산출물은 Axiom 트리에 커밋하는 대신 공개 증거 스냅샷에 실었다.

## 7) 이것이 증명하지 않는 것

"Axiom이 버그를 찾았다"로 끝내고 싶은 유혹이 있다. 그 문장은 세 가지 방식으로 거짓이다.

**솔버는 모델을 검증했지 원본 함수를 검증하지 않았다.** 캐리어는 구성된 IR이다. 원본 게이트는 스트림 결합돼 있어 의도적으로 본문으로 옮기지 않았다. canonical seal은 `EA_UNSUPPORTED: ckVarTy`로 거절됐고, 그것은 추출 경계를 측정할 수 없을 때의 정직한 답이다. SAT/UNSAT 결과는 채택된 모델에 관한 것이다. 그 모델과 원본의 대응은 루프 구조, UTF-8 테이블, 주석 집합의 정적 판독으로 뒷받침되지, 형식 증명으로 뒷받침되지 않는다.

**Axiom 저장소는 런 출력을 커밋하지 않는다.** 동결된 실험 기록의 예상 판정은 `INCOMPLETE (replay/promotion unavailable — P4 bool-binding pipeline gap)`다. 2026-10-20, 수리 후 런이 Axiom HEAD `7ae9561a9`와 재빌드한 v0.5.9 바이너리로 C1–C5 모두 `OBS`와 `ACCEPTANCE: PASS`를 관측했다. 로그와 상태 산출물은 Axiom 트리가 아니라 공개 증거 스냅샷에 실었다. PASS는 그 빌드에 대한 하네스의 관측이지, 동결된 기록을 다시 쓰는 것이 아니다.

**이것은 취약점 보고서가 아니다.** CVE도, CVSS 점수도, 심각도 주장도, upstream 권고도 없다. 범위는 문자열 내용 게이트의 TOML 부합 갭이다. `:554`의 멀티라인 게이트는 보조 반례 계열이지 1차 모델의 일부가 아니다. 발견의 완전성도 주장하지 않는다. 두 보고서는 BEL 앵커를 놓쳤고, 여기 어떤 것도 다른 결함이 없다는 것을 증명하지 않는다.

witness 바이트도 같은 주의가 필요하다. 커밋된 Phase E 로그는 SAT 실패를 보여주지만 모델의 바이트를 출력하지 않는다. `c=24`(0x18)는 갭 문서에 인용된 probe 캡처와 수리 후 커밋 메시지에 나온다. 계약이 고정하는 것은 witness **집합** — `{8, 16, 31, 127}` 밖의 모든 `forbid` 멤버 — 이지 z3의 특정 선택이 아니다. 독자는 `c=24`를 원본 Phase E 로그가 출력한 바이트가 아니라, 기록된 probe/수리 후 런에서 솔버가 고른 모델로 읽어야 한다.

## 8) 왜 실패를 공개하는가

반증은 결과다. 갭은 더 나은 결과다.

자신이 옳아 보이는 런만 공개하는 검증 시스템은 검증 시스템이 아니라 프레젠테이션 계층이다. 여기서 유용한 산출물은 궤적이다. 두 블라인드 후보 풀, 입력을 정정한 명세, 명시적 채택 행위, 한 런에 반증과 증명을 나란히 놓은 차동, 자기 반례를 막은 파이프라인 버그, 통과하기 위해 주장을 바꾸지 않기로 한 거부, 바인딩을 건드리지 않은 후속 제너릭 수리, 그리고 원본 디코더의 재생이 마침내 합의한 수리 후 런.

이 중 어느 것도 독자가 서술자를 믿을 것을 요구하지 않는다. 공개 증거 번들에는 두 탐색 보고서 원문, 에이전트가 작성한 명세, 동결된 실험 기록, 갭 문서, 런 로그, 볼트 매니페스트, 궤적(로컬 경로 redaction), 콜드 런 증명 상태, 후속 수리 커밋 메시지가 들어 있다.

Axiom 저장소가 비공개이기 때문에, 번들은 원본 저장소로 들어가는 링크가 아니라 큐레이티드 스냅샷이다. `SHA256SUMS`는 공개 바이트가 변하지 않았음을 증명하지만, 스냅샷이 비공개 원본과 같다거나 런이 실제로 일어났다는 것을 증명하지는 못한다. README가 그렇게 명시한다. 주체 쪽은 공개·고정돼 있으므로 누구나 디코더 동작을 재현할 수 있다.

```sh
git clone https://github.com/status-im/nim-toml-serialization
git -C nim-toml-serialization checkout 4aa8e2223649fc0837c490a4acfca7b8b1e756f9
sha256sum nim-toml-serialization/toml_serialization/lexer.nim
```

흥미로운 질문은 에이전트가 그럴듯한 주장을 만들 수 있는가가 아니었다. 시스템이 그 주장을 공개적으로 실패하게 두고, 실패를 온전히 남길 수 있는가였다.

그것이 남길 가치가 있는 부분이다.

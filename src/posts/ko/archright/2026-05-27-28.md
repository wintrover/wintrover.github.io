## 1. 이상한 장면

얼마 전 품질게이트를 리팩터링하면서 이상한 장면을 봤다.

CPU는 놀고 있었다.

그런데 시스템은 느렸고,
가끔은 메모리가 터졌다.

처음에는 익숙한 결론으로 갔다.

`waitForExit()`가 문제다.
비동기로 바꾸자.
이벤트 루프로 프로세스를 관리하자.

요즘이라면 자연스러운 사고다.

하지만 실제 병목은 비동기가 없어서가 아니었다.

내가 잘못 선택한 건 실행 방식이 아니라
병렬성의 단위 자체였다.

## 2. 처음에는 병렬이라고 착각했다

당시 품질게이트 구조는 이런 형태였다.

```
Gate Runner
 ├─ semaphore(maxJobs)
 ├─ startProcess()
 └─ waitForExit()
```

겉으로 보면 병렬이다.

`maxJobs=14`

설정도 있다.

그래서 나는 당연히 여러 작업이 동시에 실행된다고 생각했다.

하지만 실제로는 아니었다.

세마포어를 획득한 상태에서 `waitForExit()`가 블로킹되면서
실행 흐름 전체가 멈추고 있었다.

결과적으로:

```
configured parallelism = 14
actual parallelism   = 1
```

이었다.

그 순간 깨달았다.

문제는 스레드 수가 아니었다.

문제는 무엇을 동시에 실행 대상으로 정의했는가였다.

## 3. 내가 처음 제안한 해법: 비동기 프로세스 풀

내 첫 반응은 더 강한 비동기화였다.

구상은 이랬다.

```
asyncdispatch
↓
AsyncProcessPool
↓
event-driven completion
↓
next scheduling
```

프로세스를 논블로킹으로 실행하고,
종료 이벤트를 받아 다음 작업을 스케줄한다.

깔끔했다.

하지만 검토하면서 문제가 보였다.

내가 기대했던 수준의 asyncproc 기반 모델은
Nim 2.x 표준 라이브러리에 없었다.

가능은 하지만 이벤트 루프 전체를
설계 중심으로 끌고 와야 했다.

그리고 더 큰 문제가 있었다.

async는 국소적 변경이 아니다.

```
hook
↓
dispatcher
↓
runner
↓
gate
```

전체 호출 체인이 async/await 구조로 감염된다.

나는 병렬성을 얻기 위해
오케스트레이터 전체를 다시 만들고 싶지는 않았다.

## 4. 그래서 질문을 바꿨다

비동기가 필요한가?

아니.

내가 진짜 원하는 건 이것이었다.

> 여러 개의 프로세스를 동시에 돌리고 싶다.

이 둘은 다르다.

프로세스는 이미 운영체제가 스케줄링한다.

내가 해야 할 일은 스레드를 늘리는 게 아니라
프로세스 수명만 관리하는 것이었다.

그래서 나는 방향을 바꿨다.

## 5. 최종 선택: 동기 배치 플렉싱

최종 구조는 이렇게 됐다.

```
spawn up to maxJobs
↓
poll running()
↓
free slot
↓
spawn next
```

핵심 원칙은 단순했다.

- 프로세스 병렬성 → OS에 위임
- 오케스트레이션 → 단일 스레드 유지
- 출력 → 부모 스트림 직결
- 완료 감지만 수행

결과적으로 실행 모델은:

```
Thread Count  = 1
Process Count = N
```

이 되었다.

여기서 중요한 건
비동기를 제거한 것이 아니라

비동기를 필요 없게 만든 것이었다.

## 6. 그런데 속도보다 먼저 해결해야 할 문제가 있었다

OOM이었다.

나는 이미 품질게이트에서 두 번 메모리를 터뜨렸다.

원인은 단순했다.

병렬 실행 수가 시스템 상태와 무관했다.

남은 메모리가 500MB여도
계속 새 컴파일 프로세스를 띄웠다.

결국 병렬성이 아니라 폭주였다.

그래서 마지막으로 품질게이트 자체를 다시 설계했다.

## 7. 품질게이트를 다시 설계했다

### 1. 프로세스 병렬성은 OS에 위임한다

```
single orchestrator
+
multiple child processes
```

스레드 풀 제거.

프로세스 병렬만 유지.

### 2. 동시성은 메모리 압력으로 제한한다

```
spawn
↓
observe MemAvailable
↓
throttle
↓
continue
```

CPU 개수로 병렬도를 결정하지 않는다.

남은 메모리를 기준으로 동적으로 제한한다.

### 3. 실패는 시스템이 아니라 작업 단위로 격리한다

```
process limit
↓
gate failure
↓
system survives
```

단일 컴파일 실패가 전체 시스템 실패로 전이되지 않게 했다.

## 8. 내가 지금 사용하는 선택 기준

**동기 배치 플렉싱**

선택한다.

- 작업 대부분이 외부 프로세스
- OS 스케줄러가 이미 충분히 강함
- 실행 흐름 단순성이 중요
- 메모리 예측 가능성이 중요
- 출력 스트리밍 필요

예:

- build system
- compiler orchestration
- CI/CD
- verification engine

**비동기 멀티스레딩**

선택한다.

- 연결 수가 많음
- 이벤트 중심
- latency hiding 중요
- cancellation 필요
- 작업 자체가 IO 중심

예:

- websocket
- API gateway
- crawler
- realtime service

## 9. 결론

예전에는 이렇게 생각했다.

> 병렬성이 필요하면 비동기를 넣는다.

지금은 이렇게 생각한다.

> 병렬성이 필요하면 먼저 스케줄링 대상을 정의한다.

CPU인가.
스레드인가.
프로세스인가.

이번에는 프로세스였다.

그래서 나는 async를 넣지 않았다.

대신 병렬성의 책임을 운영체제로 옮겼다.

그리고 품질게이트는 더 빨라진 것보다 먼저,
끝까지 살아남는 시스템이 되었다.
